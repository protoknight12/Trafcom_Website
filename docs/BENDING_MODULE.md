# Модул „Абкант“ — огъване на ламарина

Офлайн програмиране и симулация за двата абканта Durma, вградено в този портал.
Цел: функционалността на AutoPOL BendSim Pro + връзка с детайли, поръчки, склад,
качество (ISO 9001) и оферти, която AutoPOL няма.

Пълно проучване и план (с матрица срещу BendSim Pro):
https://claude.ai/code/artifact/a9599c59-5137-42a9-80bf-f32b54712d83

> Този файл е спецификацията, по която се строи модулът. Следва конвенциите от
> `CLAUDE.md` — при конфликт CLAUDE.md печели.

## Машини

| Машина | Контролер | Бележка |
| --- | --- | --- |
| DURMA AD-R 40175 (175 t, 4050 mm) | Delem DA-66T **или** Durma DT-15 — да се потвърди коя е коя | вече е в `ServiceMachineCard` seed |
| Втори Durma абкант | другият от двата | **липсва** в машинния парк — да се добави като `Machine` + досие |

- **Delem DA-66T** — постпроцесорът е първи (широко поддържан формат, мрежа + USB).
- **Durma DT-15** — собствен контролер на Durma, формат без публична документация:
  нужни са експортирани програми + запитване към дилъра. Резерв: лист за оператора
  и ръчно въвеждане.
- Захващане на инструмента: най-вероятно European/Promecam — да се потвърди.
- Бекъпи на програмите и таблиците с инструменти от контролерите → в досието на
  машината (`HallMachineFile`, `machine_files/<id>/`), не в нова папка.

## Какво преизползваме (не дублирай)

| Нужда | Вече съществува | Как се ползва |
| --- | --- | --- |
| Развивка с K-фактор | `_flashing_section()` / `_flashing_unfold()` | обобщава се: K-фактор → таблица BD, при липса K-фактор с предупреждение. `/flashing` трябва да ползва същото ядро, не копие |
| DXF за лазерите | `_flashing_dxf()` — слоеве `CUT`, `BEND_UP`/`BEND_DOWN` | същата конвенция; `analyze_dxf_geometry()` вече пропуска слоеве `BEND*`, така развивката се цени директно като `Detail` |
| Каталог детайли + файлове | `Detail`, `DetailDxfFile` | 3D модел (STEP) и програмите за огъване висят на `Detail` |
| Цена/време на огъване | `Service` + `Operation` (`pricing_mode`) | услуга „Огъване“ с време от симулацията → `Operation.duration_minutes` |
| Машини и досиета | `Machine` ↔ `HallMachine` (1:1), `HallMachineFile` | параметрите на абканта стоят до `Machine`, не в нова таблица машини |
| Материали | `MaterialPrice`, `MaterialType`, `material_type_cfg()` | дебелина, якост, пружиниране; никога не разклонявай по литерален ключ на тип |
| Склад и движения | `_bump_stock()`, `DeliveryNote` (`target_type`) | инструментите се заприхождават с доставна бележка (нов `target_type='bend_tool'`) |
| Качество | `QualityCheck`, `QualityMeasurement`, `MeasuringInstrument` | измерените ъгли от цеха → QualityMeasurement; ъгломерът е MeasuringInstrument с калибриране |
| Документен контрол | `ControlledDocument` / `...Revision` | одобрена програма = контролиран документ (чернова → одобрена → остаряла) |
| Одитна следа | `log_action()`, `describe_changes()`, `ActivityLog` | всяко създаване/одобрение/изпращане към машина |
| 3D в браузъра | three.js през CDN importmap (`factory3d.html`) | същият подход за симулацията — без build стъпка |
| AI | `anthropic_client`, `CHATBOT_TOOLS` (read-only `@beta_tool`) | нови read-only инструменти (програма на детайл, наличност на инструменти) |
| Етикети | `print_label()`, `erp_number`, Code128 | QR/DM етикет на сегмент инструмент |
| Модалки | `form_dialog.js` (`data-dialog-section`, `data-frame`) | всяка форма за добавяне/редакция е dialog, списъците са read-only таблици |

## Нови модели (таблици чрез `db.create_all()`)

| Модел | Съдържание |
| --- | --- |
| `PressBrakeConfig` | 1:1 към `Machine`: работна дължина, тонаж, ход, отвор, оси (X, R, Z1/Z2), контролер (`delem_da66t` / `durma_dt15`), система за захващане |
| `BendToolCatalog` | импортиран каталог: производител (EURAM…), система, версия, изходен файл |
| `BendTool` | поансон/матрица: код, тип, профил (DXF сечение), височина, ъгъл, радиус, V-отвор, kN/m, статус (нов/прегледан/в библиотеката) |
| `BendToolSegment` | физически сегмент: дължина, `erp_number`, място, статус (на място / на машина / резервиран / за проверка / брак), брой огъвания |
| `ToolStorageLocation` | зона → шкаф → рафт → позиция |
| `BendDeduction` | BD / корекция на ъгъла по материал × дебелина × V × радиус × ъгъл; източник ръчно/измерено |
| `BendPartModel` | качен STEP/DXF към `Detail`, разпознати огъвания (JSON) |
| `BendProgram` | програма: `Detail`, `Machine`, статус, версия, файл за контролера, връзка към `ControlledDocument` |
| `BendStep` | стъпка: № огъване, ъгъл, X/R/Z, обръщане, сила, станция |
| `BendExecution` | изпълнение на цеха: оператор, поръчка/партида, измерен ъгъл по стъпка, време |

Нова колона в съществуваща таблица → `migration/migrate_add_bending_*.py`
(`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `python -m migration.<name>`).

## Файлова структура

- Маршрутите са в `app.py`, в нов раздел `# ----------------- АБКАНТ / ОГЪВАНЕ -----------------`
  (single-file конвенция).
- Тежката геометрия (STEP, разпознаване на огъвания, колизии, последователност,
  постпроцесори) е в отделен чист Python пакет `bending/` до `app.py`,
  без Flask — по прецедента на `detection.py` / `camera_pose.py`. Така се тества без база.
  - `bending/unfold.py` — общото ядро за развивка (и за `/flashing`)
  - `bending/step_import.py` — OpenCascade (`cadquery-ocp`), граф стени/огъвания
  - `bending/tools.py` — избор на инструменти, сила на огъване
  - `bending/sequence.py`, `bending/collision.py` — `trimesh` + `python-fcl`
  - `bending/post/delem.py`, `bending/post/durma_dt15.py` — постпроцесори
- Шаблони: `templates/bending_*.html`; JS: `static/js/bend_sim.js` (three.js).
- Тестове: `testing/test_bending_*.py` (assert-скриптове за `bending/`, pytest за маршрутите).
- Дълги изчисления: няма Redis/Celery в проекта. Първо синхронно с лимит на време;
  ако не стига — daemon thread по модела на `start_shelly_history_poller()`, стартиран
  само от `__main__` / `wsgi.py`, никога при import.

## Импорт на каталози с инструменти

Формати: DXF профили, STEP, CSV/Excel, PDF. PDF таблиците се извличат с Claude,
после задължителен преглед в междинна зона (нищо не влиза в симулацията без одобрение).
Първи каталог: EURAM (https://www.euram.it/download/catalog-euram.pdf) — за Promecam
стр. 9–98; таблица сила на огъване стр. 116. Профилите в DXF се искат от EURAM/дилъра.

## Профили на инструментите (реализирано)

- Профилът на поансон/матрица е **контур в mm** (`BendTool.profile_json`, върхове `[x, y, r, a]`, y нагоре): `r` = радиус на закръгляване в ъгъла
  (връх на поансона, рамо или дъно на матрицата), `a` = радиус на дъга вместо правия ръб (напр. изрязването на поансона; + вдлъбната, − изпъкнала).
  **Радиусите са данни, не рисунка** - изчисленията ги четат от контура (`bending/profile.py`: `normalize`, `outline`, `radii_report`, `derived`);
  редакторът сверява ъгъла/радиуса/V по контура с данните на инструмента и предупреждава при разлика. Поансон: най-ниската точка на върха е (0, 0);
  матрица: центърът на горния ръб е (0, 0). Контурът е основа за височини, ход на пресата и колизии, затова не е схематичен.
- **Многоканална матрица (M460.r):** един блок 60×60 с V канал на всяка страна (V50 горе, V16 вдясно, V35 долу, V22 вляво, всички 85°; рамене
  R3 при V50 и R2 при останалите, до 800 kN/m). Тя е **един инструмент**, не четири: каналите се намират от контура (`grooves()`), всеки с ширина,
  ъгъл, дълбочина, радиуси и завъртане, което го качва нагоре (`BendTool.positions`). Стъпката на програмата пази кой канал е нагоре
  (`BendStep.die_v_mm`), а изчислението на силата предлага всеки канал поотделно. Радиусите на дъната на V-тата не са на чертежа - оценени са по него
  (±1 mm) и не влияят на огъването.
- **Матрица:** каналът за матриците на абкантите е 60 mm, затова **основата** на всяка матрица (долните `base_height_mm`, задава се за инструмента)
  е точно 60 mm; нагоре матрицата може да е по-тясна. Редакторът проверява ширината по цялата височина на основата. `radius_mm` на матрицата
  е радиусът на **раменете** (краищата на V-отвора), радиусът на дъното на V-а е отделен (в контура). M460.r: корпус 60×60, рамене R2-2-2-3.
- Пази се **само работната част** на поансона. Закрепването към гредата е стандартно за пресата (европейско/Promecam, опашка 13 mm, 30 mm височина, жлеб
  за заключване), не се редактира и се добавя при чертане (`bending/profile.py: CLAMP`, `clamp_polygon()`). Каталожен DXF със закрепване
  се реже по седлото (`clip_to_seat()`, номиналната височина е до теоретичния връх - `tip_offset()`).
- Картинката е върху растер 5 mm, завъртян на 45° около върха: показва каква дължина на крило се побира до поансона.
- Редактор: `/admin/bending/tools/<id>/profile/edit` (влачене, добавяне/изтриване на точки, таблица, огледало, DXF). Каталози: профилът се
  качва като DXF към инструмента; масов импорт - при уточнен формат на каталога.

## Кинематика на машината (реализирано)

- `PressBrakeConfig` пази хода на X/R, броя упори и `kinematics_json` (Y, X, R, Z1/Z2, ширина на упора ...) от машинните параметри на контролера.
  AD-ES 2040 е **Delem DA-69S** с сервооси Y1/Y2, X (0-650), R (-45..205), Z1 (400-1560), Z2 (490-1650) и моторно бомбиране;
  `migration/seed_press_brake_configs.py` ги записва. Упорът е широк 85 mm на две нива (14/10 mm). X на стъпката е до **стената** на детайла
  (`profile.step_x`), не до средната линия. Упорът се отдръпва, когато поансонът стигне до листа. 3D: `/bending/programs/<id>/sim`.
- **Упор:** Durma DrmFinger от файловете на контролера - ниво 0 е 14 mm ръб, който стърчи 20 mm пред ниво 1 (10 mm), чието лице е стената за детайла. Към контролера се подава **оста X** (носът на ръба), не стената: когато стената е далеч от матрицата ръбът влиза под листа (`ledge`, ос = стена - 20), иначе упорът стои над матрицата и опира с лицето на ниво 0 (`face`, ос = стена). **Първи избор е челното опиране** (лицето на ниво 0, ос = стена); ръбът под листа (`ledge`) е само по заявка (`finger_section(prefer='ledge')`). Ако краят на детайла е фланец, висящ НАДОЛУ под равнината на листа, ледът не може да мине под листа през него: упорът се спуска и фланецът опира в лицето на ниво 0 (`hang` в `finger_section()`, ос = стена). `profile.finger_section()`, `step_axis_x()`; в таблицата на програмата се показва "ос X". 3D: пълните контури на нивата от `kinematics_json['finger']`, цялата машина е схематична по габаритите, а елементите се включват/изключват от панела.
- **Рамка:** профилът на страничните плочи е изчертан по чертежа на корпуса (Durma 730502001, изометрия; мащабът е от 1730 mm между рамките) и лежи в `kinematics_json['frame']` (a, b в mm от задния и долния ръб; матрицата е при a_die/b_die; плочата е ~100 mm). Гърлото е отворено напред, затова инструментът (2050) минава покрай плочите (1730). Горната греда е плоска плоча; предният долен панел носи държача на матрицата. Останалите кутии (тръби, под, пулт, предни рамена) са приблизителни - точен STEP/DXF на корпуса от Durma ще ги замени.
- **Колизии:** всичко, което се рисува, участва и в проверката (`profile.machine_env()`, `_stage_pairs()`): скоба (тяло, релса, планка), горна греда, U-държач на матрицата, маса с бомбиране, греда и колона на задния упор, упор, поансон, матрица; детайл + всяко от тях по целия ход. Детайл, по-широк от 1730 mm, се проверява и срещу профила на страничната плоча (`_plate_hits()`); планировчикът ги взема предвид (`plan(extra=...)`). Размерите на скобата и държача са приблизителни - в `profile.HOLDER` / `DIE_HOLDER_U`.
- **Подбор по дължини:** `tools.pick_segments()` взема сегменти със съвпадаща дължина на поансона и матрицата (в наличност или на машината), така че инструментът да покрие цялата дължина на огъването с най-малко излишък, после с най-малко парчета; показва се в програмата, листа и 3D (всеки сегмент е отделно парче). Дължина на огъването = размерът на детайла по линиите на огъване.
- **Детайлът разгънат и сгънат** (страница на програмата и лист за оператора, `partials/part_view.html`, `static/js/part_view.js`, `app._part_view()`): контурите (дупки, изрези, заоблени ъгли)
  от най-новия DXF на детайла (`bending/outline.py`) се показват разгънати със SVG и линиите на огъване (зелено = нагоре, синьо = надолу, с номерата на стъпките) и сгънати в 3D - в програмата с въртене
  и плъзгач „разгънат <-> сгънат“, на листа като една картинка, която се печата. Сгъването е по неутралната линия (K = 0,44, ширина на зоната = добавката за огъване), един и същ код за всеки детайл
  с DXF - не само за STEP импортите. Точният модел от STEP остава в бутона „3D“ при файловете на детайла.
- **Радиус по модела:** STEP импортът записва вътрешния радиус на всяка огъвка в слоя на DXF (`BEND_DOWN_90_R2`); `BendStep.inner_radius_mm` (миграция `migrate_add_bend_step_radius`) го пази и той заменя
  правилото 0,16 V в картинките по стъпки, колизиите и 3D (`profile.inner_radius()`), а при избор на инструмент (`tools.target_v`/`pick_tools`, планировчик) се търси V, което дава този радиус
  (r = 0,16 V, в границите 5-12 дебелини), и поансон с най-близкия радиус на върха. Предупреждение, когато избраното V дава радиус >30% различен от модела.
  **3D симулацията** също рисува истинския детайл (`bend_sim.js`: контур, дупки, изрези, заоблени ъгли): плоската развивка се реже на пластини и се тривира веднъж на стъпка (`part_view.js: flatSlices`),
  а на всеки кадър само се нанася върху текущата средна линия на разреза (`mapSlices`). Краят към упора е краят на развивката по `back_end`, при огъване надолу детайлът е обърнат (огледален по линията на огъване);
  без DXF с линии на огъване остава лентата по разреза. Рисува се посоката само на текущата стъпка.
- **Първо наличните инструменти:** планировчикът (`_plan_program()`) и автоматичният избор на инструменти (`_fill_program_tools()`) първо ползват само поансон/матрица с цял комплект секции в наличност
  (`_stock_covers()`, с запаса), и само ако така няма решение без колизии, търсят в цялата библиотека; съобщението казва кой от двата случая е и за втория препраща към предложенията (най-близък комплект, липсващи
  секции, други инструменти) в подреждането на инструментите.
- **Всички оси за ръчно въвеждане** (`partials/step_axes.html`, `_program_checks()[id]['axes']`; в таблицата на програмата, в листа за оператора и на страницата за изпълнение): Y1 = Y2 (дълбочина на върха на поансона под горната
  равнина на матрицата, за ъгъла с пружинирането, + ход от допир до листа), X (ос на упора, + стената на детайла), R (само ако е зададено в стъпката - няма изчислена стойност, докато не е известна нулата на R от контролера),
  Z1/Z2 (упорите от левия край на машината, симетрични около средата на огъването) и ъгъл (+ пружинирането). Нулата на Y в контролера може да е друга - пояснението е на листа; сверява се с пробно огъване.
- **Облицовки (/flashing) -> детайл:** при „Запиши като Детайл“ освен DXF се записва и **STEP** с огънатото тяло (`bending/flashing_step.py`: сечение в началото и в края, прави и истински дъги с точния вътрешен радиус,
  постоянна дебелина, ruled loft между двете - конусна облицовка има същите наклонени линии). Няма дупки, релефи, отщипвания (те са в DXF) и подгъвки (hem); причината се връща в `step_note`.
  Слоят на линията на огъване в DXF носи ъгъла и радиуса: `BEND_UP_90_R2` (преди бяха само `BEND_UP`, програмата налучкваше 90° и без радиус).
- **Наклонени линии на огъване (конусна облицовка):** линията е от точка до точка, не успоредна на инструмента. `bends_from_lines()` пази цялата линия (`line` = [c0, w0, c1, w1]), стъпката я пази в
  `BendStep.line_json` (миграция `migrate_add_bend_step_line`), а X е различно за двата упора: оси X1/X2 (на Z1/Z2) от линията и от реалните ръбове на детайла на тази ширина (`app._slanted_x()`,
  `outline.extent_at()`); плоският изглед чертае линиите наклонени. `api_flashing_program()` също слага стъпката по средата на линията (преди - по линията на y = 0).
  Стари програми нямат `line_json` - „Генерирай стъпките“ / „Намери последователност“ върху чернова (или нова версия) ги попълва.
- **Дали машината може да го изпълни** (`app._machine_fit()`, банер `partials/machine_fit.html` на страницата на програмата и на листа): сравнява нуждите на програмата - най-дългото огъване, най-далечния
  ход на задния упор X и най-голямата сила (на стъпката или оценка по Rm на контролера: стомана 400, алуминий 200, неръждаема 700) - с работната дължина, хода X и тонажа на машината. Ако не става:
  „НЕ МОЖЕ ДА СЕ ИЗПЪЛНИ НА ТАЗИ МАШИНА“ с причините и списък на другите абканти в системата, които го събират (най-малкият първо) с бутон „Смени машината“; ако няма такъв - казва каква дължина е нужна.
  Одобряване на такава програма се отказва. Машина без въведени параметри не се укорява (граници, които не са въведени, не се проверяват).
- **Запас на инструмента:** секциите са по-дълги от огъването - по `TOOL_MARGIN_MM` = 10 mm от всяка страна (общо +20 mm, но не повече от работната дължина на машината), за да не се работи на ръба на инструмента.
  За машина се променя с `PressBrakeConfig.kinematics_json['tool_margin_mm']` (0 връща точното покритие). В подреждането пише и дължината на огъването, и дължината със запас.
- **Няма комплект секции -> най-близкото решение** (`tools.nearest_sets()`, `app._tooling_suggestion()`): вместо само предупреждение, подреждането показва (1) най-големия комплект от наличното под дължината
  (огъване на два пъти с преместване), (2) кои стандартни секции липсват, за да стане цяло (за поансона И матрицата), (3) други поансон/матрица/V от библиотеката със същия ъгъл и V в разумни граници, които
  имат пълен комплект - с бутон „Приложи“ (`admin_bending_retool()`, само чернова). „Попитай AI“ (`admin_bending_ai_tooling()`, Claude Haiku, 30 на час) получава само фактите на планировчика (наличност, най-близки
  комплекти, алтернативи) и подрежда вариантите; не му се дава право да измисля секции. Без `ANTHROPIC_API_KEY` бутонът казва, че асистентът не е настроен - детерминираните предложения работят и без него.
- Контурите на поансоните идват от файловете на контролера (`python -m migration.import_delem_tools <папка с pun.*.dld>`); матрицата остава
  четирипосочният блок M460.r (контролерът я моделира като отделни 80 mm матрици).

## Време, цена и AI (реализирано, етапи 5-6 начало)

- **Време на детайл:** `bending/timing.py: estimate()` - огъвания, обръщане, зареждане и смяна на инструмент в програмата; подготовката на партидата се показва, но не влиза в цената.
  Времената по подразбиране (`DEFAULTS`) **не са засичани в цеха** - за машина се презаписват в `PressBrakeConfig.kinematics_json['timing']`.
  Картата „Време и цена“ на програмата записва `Operation` на детайла с почасова `Service` на машината (`admin_bending_program_operation()`); повторно натискане
  (или нова версия) обновява същата операция, а не добавя втора. Операцията е част от `Detail.total_price`, затова влиза в цената на детайла в оферти и поръчки.
- **AI:** `bending_program_info` и `bend_tool_stock` в `CHATBOT_TOOLS` - read-only и само за служители (`current_user.is_staff`), клиентите получават отказ.
- **Самообучение на пружинирането:** при изпълнение на програма всеки измерен ъгъл мести `BendSpringbackCorrection` (материал x V x дебелина) с половината от грешката
  (измерен - зададен; ограничено до +-6 градуса, грешка над 10 градуса се счита за печатна). Корекцията се добавя към оценката `springback_deg` във всички изчисления (ход, колизии, 3D, лист);
  вижда се и се изтрива в секция „Научено пружиниране“ на страницата Абкант. BD таблицата (`BendDeduction`) още не се учи от измерванията - то е за дължината на развивката, не за ъгъла.
- Остава: групиране по общи инструменти (пакетна обработка), автоматично учене на BD, проверка на технологичността за клиенти.

## Импорт от SolidWorks (реализирано)

- `.sldprt`/`.sldasm` са затворен формат - чете ги само SolidWorks. Приема се **STEP (AP214)** - детайл или сглобка (`/admin/bending/step-import`, бутон „Импорт от SolidWorks (STEP)“ на страницата Абкант).
  Родни файлове се отказват с обяснение как да се запише STEP; листови детайли може да се изнесат и направо като DXF (Flat-Pattern -> Export).
- `bending/step_import.py` (OpenCascade през `cadquery-ocp-novtk`): `read_parts()` обхожда структурата на сглобката (XCAF), брои колко пъти се ползва всяка част
  (вложени подсглобки се умножават); `analyze()` познава ламарината по геометрията - всички стени са равнини/цилиндри, всяка равнина има успоредна на дебелина t, всяка
  огъвка - коаксиален цилиндър с радиус +-t, обемът отговаря на лист с постоянна дебелина (болтове, греди, плочи >25 mm се отхвърлят с причина);
  `flat_pattern()` развива по-голямата страна: равнините запазват формата си, огъвката става лента с дължина по стратегията на `bending/unfold.py` (K-фактор 0,44, докато няма BD таблица
  за материала); `write_dxf()` пише `CUT` + `BEND_UP_<ъгъл>`/`BEND_DOWN_<ъгъл>` (гледка отвън, UP = огъва се към зрителя) - същата конвенция като `/flashing`, затова `Detail` с този DXF
  се цени, огъва и програмира както всеки друг.
- Екранът за преглед показва всички части: ламарината е отметната (име, материал с най-близка дебелина), останалото е сиво с причина. „Създай детайли“ прави `Detail` + DXF; име, което вече съществува,
  се преизползва (не се дублира). По избор се прави и `Product` от сглобката с броя на частите (само листовите).
- **Файлове и 3D:** към всеки създаден `Detail` се записва и собствен STEP файл на частта (`<име>.step`, в списъка с файлове на детайла, заедно с DXF развивката; вече съществуващ детайл без STEP го получава при следващ импорт).
  Бутон „3D“ до файла отваря `/details/files/<id>/view3d` (three.js, въртене/мащаб, изгледи, ръбове, мрежа); мрежата от триъгълници идва от `bending.step_import.mesh()` през `/details/files/<id>/mesh`
  (допустимо отклонение според размера на частта, до 300 000 триъгълника). Само за администратори, като изтеглянето.
- Не се поддържа (връща причина, не гадае): конуси/сплайнове, две огъвки подред, плоскост направо в плоскост, затворени кутии (развивката е дърво). Ъглите в имената на слоевете са цели градуси.
  Няма проверка срещу реалната развивка на SolidWorks - сравнете дължината на първата развивка с неговата и ако се различава, нагласете K-фактора (`flat_pattern(strategy=...)`).
- Тестове: `testing/test_step_import.py` (STEP файловете се генерират от `testing/step_fixtures.py`; ръчно пресметнати развивки на L и U).

## Етапи

1. **Развивка и библиотеки** — `bending/unfold.py` (ядро от flashing + BD таблици),
   `PressBrakeConfig`, `BendTool`/`BendToolSegment`/`ToolStorageLocation`, импорт EURAM,
   STEP → огъвания → DXF развивка към `Detail`.
2. **Ръчно програмиране и лист за оператора** — `BendProgram`/`BendStep`, лист за
   таблета, измерени ъгли → `QualityMeasurement`, контролиран документ.
3. **Автоматика и 3D симулация** — избор на инструменти, последователност, задни упори,
   колизии, `bend_sim.js`.
4. **Постпроцесори** — Delem DA-66T първи, после Durma DT-15.
5. **Пакетна обработка и оферти** — групиране по общи инструменти, време/цена в офертата,
   самообучаващи се BD таблици от измерванията.
6. **AI и клиентски достъп** — read-only инструменти в `CHATBOT_TOOLS`, проверка на
   технологичността при качен модел (`client_allows()` / `@app_access_required`).
